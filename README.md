# court-monitor

Полуавтоматическая система мониторинга уголовных дел по открытым источникам.

Собирает публичные материалы, извлекает из них факты (статьи УК, даты, ФИО) и
показывает оператору кандидатов на совпадение с реестром Росфинмониторинга.

**Ничего не публикует и ничего не решает сама.** Совпадение подтверждает
человек, каждое решение пишется в аудит-лог.

---

## Установка — один раз

```bash
make install     # зависимости
make init-db     # схема БД (SQLite по умолчанию)
make doctor      # проверка, что всё на месте
```

`make doctor` должен закончиться без проблем. Если он ругается — читайте
вывод, он называет конкретную причину; чаще всего это отставшая БД, лечится
`make migrate`.

Языковая модель и spaCy-NER по умолчанию выключены — система работает без них
на детерминированных правилах. Подключение модели описано в
[шаге 4](#необязательно-подсказка-языковой-модели).

### Настройка Firefox для fedsfm.ru

Сайт `fedsfm.ru` использует сертификат российского CA, которого нет в системном
хранилище. Проект пинит CA для HTTP-клиента (`config/ca/fedsfm_ru_chain.pem`),
но Firefox использует своё хранилище NSS. Чтобы открывать сайт в Firefox:

```bash
# Импорт CA в Firefox profiles
uv run python scripts/import_fedsfm_ca_firefox.py
# Перезапустите Firefox
```

Скрипт импортирует CA во все Firefox profiles через `certutil`. После импорта
сайт будет открываться без предупреждений о сертификате.

Для других приложений (curl, wget, Python без pinned CA) можно установить CA
в системное хранилище:

```bash
sudo scripts/install_fedsfm_ca.sh
```

**Важно:** на Arch Linux Firefox не использует системное хранилище по умолчанию,
поэтому для Firefox нужен именно первый способ.

## Рабочий цикл

Пять шагов. Первые два нужны редко, три последних — это собственно работа.

### Шаг 1. Обновить список источников *(редко)*

Список каналов и сайтов лежит в `config/source_registry.yaml`. Он меняется
нечасто, так что этот шаг — не для каждого запуска.

```bash
uv run court-monitor import-source-registry --from-airtable   # предпросмотр
uv run court-monitor import-source-registry --from-airtable --no-dry-run
uv run court-monitor check-sources                            # кто ещё отвечает
```

`import-source-registry` по умолчанию **только показывает**, что импортирует.
Чтобы записать файл, нужен явный `--no-dry-run`.

`check-sources` делает по одному запросу на источник и говорит, кто отвечает,
а кто блокирует. Полезно, когда сбор вдруг стал приносить меньше материалов.

### Шаг 2. Загрузить перечень Росфинмониторинга *(раз в несколько дней)*

Это та база, с которой сопоставляются найденные в документах имена. Без неё
шаг 4 не найдёт ничего.

```bash
uv run court-monitor fetch-source fedsfm --live --replace
```

Загружает ~21 500 записей о физлицах напрямую с `fedsfm.ru`. VPN не нужен —
сайт не блокирует по географии, там достаточно правильно проверить TLS
(детали в [`docs/configuration.md`](docs/configuration.md)).

**`--replace` здесь по делу.** Росфинмониторинг публикует перечень целиком, а
не приращение, поэтому правильная операция — замена, а не дозапись. Импорт
поверх старого корректен, только если оба списка несут одни и те же поля, а
это не так: в CSV-выгрузке даты рождения нет вообще, на живой странице она
есть у всех — тот же человек даёт два разных ключа дедупликации и попадает в
базу дважды. Замер: 21 277 из 22 156 имён пересеклись, база выросла до 43 667.

Замена откажется работать, если удалит уже принятые решения оператора
(удаление записи каскадом уносит её кандидатов) — подавляется через `--force`.

Если сеть недоступна, можно импортировать из файла:

```bash
uv run court-monitor fetch-source fedsfm --file <path> --dry-run   # посмотреть
uv run court-monitor fetch-source fedsfm --file <path>             # записать
```

### Шаг 3. Собрать материалы и найти кандидатов

Одна команда: все sudrf-источники + Telegram-каналы, затем сопоставление.

```bash
uv run court-monitor run-all --live
```

Без `--live` работает на фикстурах и в сеть не ходит — так проверяют, что
конвейер цел, не трогая чужие сайты.

Вывод — построчная сводка по каждому источнику. Смотреть надо на две вещи:

- **`blocked`** — источник ответил, но отказал. Это не сетевой сбой, это
  осознанный отказ на той стороне; такой источник не чинится повтором.
- **`failed`** — сбой разбора. Материалы при этом уже сохранены, и каждый сбой
  попадает в очередь проверки (шаг 5), а не только в лог.

`--verbose` включает полный JSON-лог по каждому документу.

### Шаг 4. Разобрать кандидатов — это основная работа

```bash
make run-web     # http://127.0.0.1:8010
```

Откройте `/matches`. Каждый кандидат — предположение, что имя из документа и
запись в реестре относятся к одному человеку. Дальше решает оператор.

Страница называется **«Очередь решений»** и устроена как ручная очередь, а не
как таблица отладочных чисел. В каждой строке показано:

- **В документе → В реестре** — какое имя найдено в тексте и с какой записью
  перечня оно сравнивается;
- **сигналы** — сколько в перечне однофамильцев и встречалось ли это имя в
  других документах;
- **подсказка по доказательствам** — например, что совпали только фамилия и
  имя, а даты рождения в тексте нет;
- **«Принять решение»** — открыть карточку кандидата.

Карточка кандидата сначала показывает блок **«Что нужно решить»**: имя в
документе, имя в реестре, дату рождения из реестра и наличие/отсутствие даты
или места рождения в тексте. Если совпали только фамилия и имя, подтверждать
нельзя: проверьте цитату, оригинал документа и контекст. Если документ не даёт
дополнительных признаков того же человека, безопасное решение — отклонить или
оставить кандидата в ожидании.

Технический score не является решением. Он спрятан в диагностике карточки и
нужен только для разбора того, какие правила сработали.

**Почему у многих кандидатов score 0.50 и на что тогда смотреть.** Порог 0.45
проходит совпадение фамилии и имени — 0.50. Всё, что могло бы поднять или
опустить оценку (дата и место рождения), в реестре есть, но **в текстах
документов почти отсутствует**: 5 упоминаний даты рождения на 379 документов,
мест рождения — ноль. То есть однофамильца от фигуранта скор отличить не может
в принципе, и доверять числу как ранжированию нельзя.

Поэтому очередь и карточка показывают то, чего в скоре нет:

- **сколько в реестре однофамильцев** — один Шульман и 64 Иванова при
  одинаковом 0.50 это принципиально разные ситуации;
- **другие упоминания того же человека** с цитатами — фигурант нескольких
  материалов и единичное упоминание весят по-разному.

Решение (подтвердить / отклонить) требует комментария и пишется в аудит-лог
вместе с тем, кто его принял. Подробный операторский мануал с примерами:
[`docs/manual-match-review.md`](docs/manual-match-review.md).

То же самое из CLI:

```bash
uv run court-monitor list-matches --status pending
uv run court-monitor show-match <id>
uv run court-monitor confirm-match <id> --comment "..." --operator "имя"
uv run court-monitor reject-match <id> --comment "..." --operator "имя"
```

#### Необязательно: подсказка языковой модели

Скоринг здесь бессилен по причине, описанной выше, — но человек, читая текст,
всё-таки различает случаи. Ровно это можно поручить модели: она читает документ
и говорит, согласуется ли описанное лицо с записью реестра, **приводя цитату**,
по которой вы можете её проверить.

Выключено по умолчанию. Включается настройками в `.env`:

```ini
CM_LLM_MODE=deepseek
CM_LLM_BASE_URL=https://api.deepseek.com
CM_LLM_MODEL=deepseek-v4-pro
CM_LLM_API_KEY=sk-...
```

```bash
uv run court-monitor judge-matches                  # разобрать очередь
uv run court-monitor judge-matches --limit 5        # только первые пять
uv run court-monitor judge-matches --rejudge        # пересмотреть уже разобранные
uv run court-monitor judge-matches --verbose        # с расходом токенов в логе
```

Вердикт появится тегом в `/matches` и блоком на карточке кандидата.

**Это подсказка, а не решение.** Суждение не входит в `score`, не меняет статус
кандидата и никого не подтверждает — как и всё остальное в системе, решает
оператор. Модель может ошибаться, поэтому цитата обязательна: проверяйте вывод
по ней, а не по уверенности формулировки.

**Что это даёт на практике.** Прогон по 14 кандидатам рабочей базы: 13 раз
«мало данных», один раз «опровергнуто» — по упоминанию должности «зампред
Совбеза» модель поняла, что речь о Дмитрии *Анатольевиче* Медведеве, тогда как
в реестре Дмитрий *Максимович* 2003 года рождения. Скоринг видел «Медведев
Дмитрий» и ставил 0.50.

Промпт намеренно осторожен: ложное «совпадает» дороже ложного «не знаю», отсюда
столько «мало данных». Если для ваших материалов это слишком консервативно —
формулировка правится в `src/court_monitor/llm/disambiguation.py`, менять код
не нужно. Учтите и то, что **вердикты недетерминированы**: один и тот же
кандидат между прогонами может получить разные ответы. Это ещё одна причина,
по которой они не участвуют в `score`.

**Цена и скорость.** Около 10 секунд и порядка 0.1 цента на кандидата
(DeepSeek `v4-pro`, ~800 входных токенов). Разбор всей очереди из 14 кандидатов
— полторы минуты и полтора цента.

**Провайдер не зашит.** Клиент говорит на OpenAI-совместимом формате, а адрес
берётся из `CM_LLM_BASE_URL`. Локальный `vLLM`/`Ollama` или другой хост
подключается сменой этой строки — код не меняется. Это же снимает вопрос об
отправке ФИО фигурантов во внешний сервис, если он для вас существенен:
DeepSeek — китайская компания, и запросы уходят на её инфраструктуру.

Если модель недоступна или ключ неверен, конвейер деградирует: команда честно
скажет, что не смогла, а данные останутся нетронутыми.

### Шаг 5. Разобрать очередь проверки

Страница `/review`. Сюда автоматически попадает всё, что система не смогла
обработать сама — в первую очередь сбои парсера. Смысл очереди в том, что
сломанный селектор иначе молча теряет материалы: в логе строчка есть, а
заметить её некому.

```bash
uv run court-monitor list-review-items --status pending
uv run court-monitor resolve-review-item <id> --comment "починил селектор"
uv run court-monitor resolve-review-item <id> --dismiss --comment "не наш случай"
```

Починив парсер, документ можно перепарсить:

```bash
uv run court-monitor reprocess-document <id>
```

Если по документу уже приняты решения о совпадениях, команда откажется
работать — перепарсинг их уничтожит. Подавляется через `--force`, осознанно.

### Когда исправлено само извлечение

Правки экстрактора **не доходят до уже собранных данных**: факты остаются
такими, какими их вытащили при загрузке. Чтобы применить исправление ко всему
корпусу:

```bash
uv run court-monitor reprocess-all --dry-run   # посмотреть дельту
uv run court-monitor reprocess-all             # применить
uv run court-monitor generate-matches          # кандидаты считались по старым фактам
```

`generate-matches` обязателен: удаление фактов каскадом уносит и кандидатов.

Та же защита, что у `reprocess-document`, но проверяется один раз на весь
корпус — запуск, который снёс бы решения оператора, не должен успеть удалить
половину фактов до первого защищённого документа.

## Что извлекается из документов

| Что | Пример |
|---|---|
| Статья УК | `п. «а» ч. 2 ст. 205 УК РФ` |
| Дата | `2026-04-02 (дата приговора)` |
| ФИО | `Иванов Иван Иванович (уверенность 0.95)` |

Извлечение — regex; опционально включается NER (`CM_NER_MODE=spacy`),
работающий в дополнение к нему. Подробности — в
[`docs/ai-context/extraction.md`](docs/ai-context/extraction.md).

## Если что-то пошло не так

| Симптом | Куда смотреть |
|---|---|
| Любая непонятная ошибка | `make doctor` — называет конкретную причину |
| `no such column` | БД отстала от миграций → `make migrate` |
| Источник ничего не приносит | `check-sources`; счётчик `blocked` в сводке `run-all` |
| Документы есть, фактов нет | `/review`, `show-document <id>` |
| Кандидатов нет вообще | Загружен ли перечень РФМ (шаг 2): `list-person-records` |
| `judge-matches` говорит «LLM не настроен» | Заданы ли все четыре `CM_LLM_*` в `.env` |
| Суждений нет, ошибок нет | Возможно, все кандидаты уже разобраны — `--rejudge` пересмотрит |

## Ограничения, о которых надо знать заранее

- **Аутентификации в вебе нет** (D-007). Интерфейс сидит на loopback; при
  выносе наружу вы получите предупреждение — оно не декоративное.
- **Судебных источников нет, и туннель в РФ не помогает.** Проверено
  замером: `bsr.sudrf.ru` не отвечает ни из Казахстана, ни через российский
  VPN (соседние хосты той же подсети при этом открываются за 0.1 с) — он
  недоступен всем, а не нам. Домены судов отдают 404. Причина глубже
  блокировок: официальные акты обезличиваются по ст. 15 ФЗ-262, поэтому
  `vsrf.ru`, `sudact.ru` и пресс-релизы СК и Генпрокуратуры не содержат ФИО
  фигурантов даже там, где доступны. Разведка целиком — в
  [`docs/ai-context/known-risks-and-notes.md`](docs/ai-context/known-risks-and-notes.md);
  воспроизвести замер: `scripts/probe_sudrf.py`. Единственный живой источник —
  Telegram-каналы.
- **Скор не ранжирует.** См. шаг 4: в документах нет дат рождения, поэтому
  0.50 стоит почти у всех и означает «проверь руками», а не «вероятно».
- **Планировщика нет.** Сбор запускает человек — из `/jobs` или командой.
- **Суждение модели не воспроизводимо** и по умолчанию выключено. Если
  включите — помните, что один и тот же кандидат между прогонами может дать
  разные вердикты, поэтому они и не входят в `score` (шаг 4).
