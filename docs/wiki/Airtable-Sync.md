# Синхронизация справочников из Airtable

Airtable — внешняя админка, PostgreSQL — рабочее хранилище. Обработка статей к
Airtable не обращается никогда: кнопка переносит справочники один раз, дальше
система читает только базу.

## Как читается Airtable без токена

Проверено на живых данных 30.09.2026. Ни токена, ни входа, ни выгрузки вручную.

Публичная ссылка вида `https://airtable.com/{applicationId}/{shareId}` отдаёт
страницу, в которой `window.initData` содержит `sharedViewId` и `accessPolicy`.
`accessPolicy` — **подписанная** строка JSON: `signature`, `expires`, `shareId`,
`applicationId`, `generationNumber` и список `allowedActions`. Именно она и есть
право на чтение; подпись живёт неделями — наблюдавшаяся 30.09.2026 была действительна
до 22.10.2026.

Дальше анонимный запрос:

```
GET https://airtable.com/v0.3/view/{viewId}/downloadCsv
```

Параметры строки запроса:

- `accessPolicy` — та самая подписанная строка; **без неё ответ не падает, а уходит
  в HTML-оболочку приложения**. Это самое опасное здесь: 200, который читается как
  «строк нет», а значит как «список пуст»;
- `requestId` — любой, `req` плюс 12 символов;
- `stringifiedObjectParams` — `{"includeBlanks":false}`.

Заголовки, без которых не работает:

```
x-airtable-application-id: {applicationId}
x-airtable-inter-service-client: webClient
x-airtable-inter-service-client-code-version: cf32083c89c00ebe303ad7d79334a82e1c86f2a7
x-airtable-page-load-id: {pageLoadId со страницы}
x-requested-with: XMLHttpRequest
x-time-zone: Asia/Almaty
x-user-locale: en
referer: {сама публичная ссылка}
```

Что стоит знать, потому что об этом легко ошибиться:

- **CSRF-токен шлётся НЕ надо и нельзя.** `x-airtable-csrftoken` превращает
  анонимное чтение в вызов приложения, и ответ — `401 AUTHORIZATION_REQUIRED`.
  Право на чтение — подписанная политика, а не токен.
- `downloadCsv` без заголовка `x-time-zone` отвечает `400`, называя его в тексте.
- `readSharedViewData` отдаёт `application/msgpack` (68 МБ на 14 306 строк) и требует
  разбора msgpack. `downloadCsv` отдаёт готовый CSV и лишних зависимостей не требует —
  берём его.
- Подпись получать не нужно: `accessPolicy` в странице уже подписанная. Ничего
  не подписываем локально.

Отпечаток браузера даёт `curl_cffi` с `impersonate="chrome146"` — тем же приёмом, что
в `torrent-loader`. Обычный `curl` получает стену входа: 306 КБ со «Sign in» вместо
гостевой страницы в 119 КБ. Пакет лёгкий, 12.9 МиБ, слой torch не затрагивает.

Реализация: `airtable/share.py` (протокол), `airtable/links.py` (выбор источника и
откат), `airtable/service.py` (`build_sync_source`).

## Порядок выбора источника

1. **API** — лучший: несёт id каждой записи, переименование человека это обновление,
   а не вторая строка.
2. **Публичные ссылки** — автоматически и без токена; для базы, чужой владельцу.
3. **Выгруженные файлы** — последний резерв, требуют ручной выгрузки.

Токен без прав на базу (у чужой базы он есть именно такой) больше не роняет всё
сразу: для каждого списка, у которого есть ссылка, чтение уходит по ней, и в отчёте
видно, кто именно прочитан по ссылке.

Список без источника **пропускается**, а не читается как пустой. «Нечего читать» и
«список пуст» — разные вещи, и второе здесь означало бы стереть 13 765 человек.

| Статьи | `appExample0000001/shrExample0000002` | 559 строк, одна колонка `Полная статья` |
| Источники | `appExample0000002/shrExample0000001` | 69 строк: `Название`, `Юзернейм`, `Ссылка`, `Тип/тематика` |

Первая ссылка — тот же файл, что лежал в `~/Downloads/ЕНБВ. Кейсы по
персоналиям.csv`; вторая — `список статьей для мониторинга.csv`; третья —
`источник мониторинга(1).csv`.

**Первый список — это «Найденные люди», а не перечень Росфинмониторинга.** Это
люди, которых мы уже знаем. Официальный перечень публикует fedsfm.ru, и только он
может сказать, что человек в перечне. Раньше список из Airtable снимком попадал в
слой «возможно в перечне» и убирал людей из новых находок, то есть утверждал о них
то, чего не знает; теперь он не создаёт снимка вовсе, и утверждение остаётся там,
где оно истинно.

**Источники ведутся в другой базе** — `appExample0000002`, не в той, что перечень и
статьи. Это выяснилось чтением списков, а не предположением; ссылки взяты из выгрузки
чата `ChatExport_2026-09-28/messages.html`.

«Найденные люди» и «Росфинмониторинг» — это одни и те же 13 765 человек из одного
представления, поэтому «Найденные люди» читаются по ссылке перечня, если своей не
задано. Названия на странице оставлены как есть.

Пятый справочник — **статьи, которые нас интересуют** (таблица `criminal_articles`,
миграция `c3d4e5f6a7b8`). Ключ `article_key` хранит номер так, как его пишет
конвейер (`entity_group_charges.article` — «205.2»), иначе список не встретился бы с
обвинениями из статей. Строка без номера не пишется: из 559 живых строк такая одна
(«Нет информации»), и её количество — единственный сигнал, что список испорчен.

Кодекс в ключ не входит: «ст. 30 УК РФ ч. 1» и «ст. 30 УК ЛНР ч. 1» дают общий ключ
«30.1». Это ограничение таблицы обвинений, в которой кода тоже нет; пока списком
никто не ищет, оно стоит только счёта, а тем, кто будет искать, об этом надо знать
заранее.

## Настройка

```sh
AIRTABLE_SHARE_URL_KNOWN=https://airtable.com/appExample0000001/shrExample0000003
AIRTABLE_SHARE_URL_ARTICLES=https://airtable.com/appExample0000001/shrExample0000002
AIRTABLE_SHARE_URL_SOURCES=https://airtable.com/appExample0000002/shrExample0000001
# AIRTABLE_SHARE_URL_OFFICIALS — «Должностные лица» в Airtable не ведутся
# AIRTABLE_SHARE_URL_RFM принимается как прежнее имя ссылки на список людей,
# чтобы уже заполненное окружение продолжало работать.
AIRTABLE_TOKEN=   # оставьте пустым: без прав он всё равно 401
```

Собственная таблица оператора по перечню РФМ в эту синхронизацию не входит: у неё своя
настройка `RFM_TABLE_SHARE_URL`, и читает её сверка с перечнем
([Rosfinmonitoring](Rosfinmonitoring.md#таблица-оператора)).

## Список, который заменяется целиком, и предохранители

Список, прочитанный из представления Airtable, — это **копия** того, что
представление говорит сегодня. Ушёл из представления — должен уйти и из копии, иначе
человек, удалённый из Airtable, остаётся в базе навсегда. Поэтому `Найденные люди`
и `Статьи` заменяются содержимым выгрузки. `Источники` и `Должностные лица` — нет:
там строка это решение человека, и никакая выгрузка его не отзывает.

Очистка происходит **в одной транзакции с записью**: сбой в середине оставляет
прежний список целиком, а не наполовину обновлённый.

Перед удалением — три предохранителя:

1. тело короче, чем обещал сервер, — передача оборвалась;
2. CSV без заголовка — столбцы неизвестны, а строки не пусты, а нечитаемы;
3. число строк не обвалилось против того, что мы сами записали в прошлый раз
   (ниже четверти — отказ; меньше ста строк — отказ всегда).

Чего проверить нельзя: **ожидаемого числа строк у публичного представления нет
нигде** — ни в странице, ни в заголовках ответа, ни в самой выгрузке. Так что третий
пункт — правдоподобие, а не доказательство полноты.

**Предел намеренный:** список меньше ста строк нельзя опустошить кнопкой, потому
что ссузившийся по ошибке взгляд и решение «вычеркнуть всех» выглядят одинаково.
Отказ виден в отчёте и говорит, что делать вручную.

## Официальный перечень Росфинмониторинга

`rosfinmonitoring/download.py`. Сайт отдаёт `403` на выдуманный User-Agent, и перечень
приходилось сохранять руками и загружать на сайт. С отпечатком браузера отдаёт `200`.

- адрес: `https://www.fedsfm.ru/documents/terrorists-catalog-portal-act`. На
  `/documents/terr-list`, который указан на сайте, перечня нет — это страница-заглушка
  в 23 КБ; правильный адрес найден среди ссылок внутри сохранённой страницы;
- проверено: скачанное **побайтово совпадает** с перечнем, сохранённым вручную
  (4 305 049 байт, 23 013 дат рождения);
- `verify=False` больше не нужен: в обход стены он не участвует, а проверку
  сертификата отключать незачем;
- ответ проверяется на то, что это перечень. `403` и «технические работы» — тоже `200`
  или почти, и такой ответ не должен заменить снимок из 23 000 человек пустым.

## Список должностных лиц: единственный, который правят здесь

Остальные четыре справочника приезжают из Airtable, а этот — нет: человек попадает в
список потому, что кто-то решил, что фигурантом ему быть нельзя, и это решение
человеческое, а не копия. Поэтому он и редактируется в самой консоли.

- `/ui/airtable/officials` — форма добавления, сам список и выгрузка CSV;
- шаг 4 («Найти фигурантов») сам добавляет сюда тех, перед чьим именем в текстах стоит
  «судья», «прокурор», «министр», «губернатор» и т. п. (в двух упоминаниях или в половине
  всех), с категорией по должности и причиной «автоматически: …». Добавленные остаются,
  даже если в другой статье должности перед именем нет. Снятого вручную и человека с
  отметкой на карточке он не возвращает и не добавляет;
- ниже формы — «Предложения системы»: люди, которых только модель считает должностными
  (по тексту должности нет). Сами они в список не попадают: модель называла должностным
  арестованного полицейского. Кнопка «Добавить в список» принимает предложение как решение
  человека (причина «предложено моделью, принято вручную»); в силу оно вступает при
  следующем «Найти фигурантов»;
- порядок приоритета при определении должностных: отметка на карточке (в любую сторону) →
  список → должность в текстах → ответ модели. Отметка «не должностное лицо» побеждает и
  строку списка;
- снятие — это `active = false`, **не удаление**: «мы посмотрели, он не должностное
  лицо» — это ответ, и список, который его не помнит, будет задан тот же вопрос
  заново и кем-то другим;
- имя, под которое не подошёл ни один человек, всё равно пишется, но страница говорит
  об этом прямо — сказать «система считает его должностным» было бы враньём;
- формы разбираются вручную: `python-multipart` в проекте нет и быть не должен, он
  пересобирает слой с torch.

## «Найденные люди» в «Результате»: кто уже есть в вашей базе

Таблица «Найденные люди» нужна не только как справочник: по ней «Результат» говорит, есть ли
найденный человек в вашей базе. Новый для вас — тот, кого там нет. Колонка и фильтр
«В базе Airtable» на странице, колонка «В базе Airtable» в Excel (с тем же фильтром) и блок
«База Airtable» в досье (`src/entities/known_base.py`).

В таблице нет ни даты рождения, ни региона, поэтому сверка идёт **только по имени** — и
ответ говорит, насколько он надёжен:

| ответ | что это значит |
|---|---|
| **есть в базе** | ровно одна запись с этим именем целиком (те же слова, порядок и регистр не важны) |
| **вероятно, есть в базе** | одна запись, но имя записано иначе: в базе есть отчество, а в новости нет, или наоборот |
| **тёзки в базе: N** | подходят несколько записей; по имени нельзя понять, какая, и система не выбирает |
| **нет в базе** | никого с таким именем: вероятно, новый человек |

Что учтено: «ё» и «е», регистр, порядок слов, написание в скобках («Лагода Роман Александрович
(Лагода Роман Олександрович)» — одна запись, читаются оба написания, украинское тоже),
латиница. Что не человек, пропускается: записи с цифрой («Житель Курской области 1»).
Имя из одного слова ни с чем не сверяется. Неактивные записи не считаются.

Важно: **«есть в базе» — не «неинтересно»**. Новое дело или приговор по человеку, который у вас
уже есть, остаётся новостью: колонка «Свежая новость» стоит рядом. А «нет в базе» может быть
и человеком, записанным у вас иначе (другая транслитерация): сверка по имени не видит
таких. Пока таблица не загружена («База Airtable» → синхронизация), колонка пуста и фильтра нет:
«нет в базе» без базы ничего бы не значило.

## Справочники в PostgreSQL

| список | ключ | таблица |
|---|---|---|
| Источники | `sources` | `sources`; по `base_url`, обновляются только `name` и `active`, новых строк не заводится |
| Найденные люди | `known_persons` | `airtable_known_persons` |
| Должностные лица | `officials` | `excluded_persons`; правятся в консоли, из Airtable не читаются |
| Статьи | `articles` | `criminal_articles` |

Снимок из Airtable не заменяет официальный: официальная сверка даёт `confirmed`, только
из Airtable — `probable`. Обе стороны замкнуты, чтобы списки не смешивались:
`latest_imported_snapshot()` и `latest_snapshot_id()` в
`rosfinmonitoring/snapshot_lookup.py` отбрасывают снимок Airtable,
`CandidateQueryService.get_candidates()` его отвергает.

Таблица `excluded_persons` называется по-старому: список стал «Должностными лицами»
позже. Переименование требует правки `orm_models.py` и `maintenance.py`, а в них
незакоммиченная работа другой сессии, которую коммит захватил бы. Имя внутреннее; на
странице, в файле `officials.csv` и в переменной `AIRTABLE_OFFICIALS_TABLE` везде
«Должностные лица».

## Файловый режим

Остаётся резервом. Таблица `airtable-import/` примонтирована в контейнер как `/import`.

| файл | справочник | обязательные столбцы |
|---|---|---|
| `sources.csv` | Источники | `base_url` (он же `Ссылка`, `Адрес`, `URL`) |
| `rfm_persons.csv` | Росфинмониторинг | `full_name` (он же `ФИО`, `Преследуемый`, `Имя`) |
| `known_persons.csv` | Найденные люди | `full_name` |
| `officials.csv` | Должностные лица | `full_name` |
| `articles.csv` | Статьи | `Полная статья` (он же `Статья`, `article`) |

- **пустой файл не трогает данные** — файл только с заголовком отклоняется с ошибкой,
  а не читается как «список пуст»; отсутствующий файл просто пропускается;
- сопоставление идёт по ФИО, не по id Airtable: переименование человека даст вторую
  строку, а не обновление;
- даты приходят как `July 12, 1980` — импортер понимает; при незнакомом формате в
  отчёте будет заметно меньше людей «с датой рождения»;
- строки без отметки `✦Росфинмониторинг` в перечень не попадают;
- галочка приходит как `1 checked out of 1` / `0 checked out of 1`.
