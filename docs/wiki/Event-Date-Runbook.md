# Runbook: миграция `event_date` и пересборка извлечённых фактов

## Зачем это нужно

Миграция `q1w2e3r4t5y6` (`event_date` — дата самого события, а не дата публикации) меняет
данные, которые читает интерфейс, поэтому её нельзя применять одной операцией вместе с
merge или вместе с повторной обработкой статей.

Последовательность состоит из **пяти** шагов, и порядок обязателен. Две причины:

- повторное извлечение **не заменяет** старые события, а добавляет новые рядом с ними;
  новые события попадают в интерфейс только после пересборки групп людей;
- `collect-entities` при пересборке **стирает** роли (`entity_group_roles`) и политические
  вердикты (`entity_group_politics`). Без следующих двух шагов список кандидатов и
  «политические дела» остаются пустыми.

Все шаги прогнаны подряд на полной копии рабочей базы (4617 статей, 17622 события) с
поднятым рядом приложением; ниже приведено, что именно видел пользователь на каждом шаге.

## Быстрый сценарий

Каждая строка — отдельный шаг. **Дальше не идти, если шаг не завершился успешно.**

```bash
# 0. Остановить API: промежуточные состояния не должны быть видны пользователям
docker compose stop api

# 1. Резервная копия. Дамп пишется на хост: у контейнера postgres нет bind-mount,
#    и файл внутри него пропал бы вместе с контейнером
mkdir -p backups
docker compose exec -T postgres \
  pg_dump -U court_monitor -d court_monitor -Fc \
  > backups/court_monitor_before_event_date.dump
ls -la backups/court_monitor_before_event_date.dump   # файл не пустой

# 2. Миграция: снимает подменённые даты, кладёт их в backup-таблицу
docker compose run --rm migrate

# 3. Повторное извлечение (правила, без LLM). Долгий этап — дождаться вывода
docker compose run --rm api court-monitor extract-entities --limit 5000 --workers 4

# 4. Пересборка групп людей. ВНИМАНИЕ: стирает роли и вердикты
docker compose run --rm api court-monitor collect-entities

# 5. Роли обратно (платная модель, бюджет прогона)
docker compose run --rm api court-monitor find-figurants

# 6. Вердикты и производные от них стадии обратно (платная модель)
docker compose run --rm api court-monitor find-political

# 7. Проверка (см. «Проверка»), затем вернуть API
docker compose start api
```

Шаги 5 и 6 обращаются к модели. Бюджет одного прогона — `ENTITY_MODEL_BUDGET_USD`
(по умолчанию $2). На копии оба шага прогнаны с `ENTITY_MODEL_BUDGET_USD=0`: правила
отработали, кэш ответов переиспользован, `asked_now: 0`, траты не изменились. Без этого
лимита прогоны на корпусе этого размера могут стоить до $2 каждый — считать бюджет
отдельно.

## Что видит пользователь на каждом шаге

Проверено на копии: приложение поднято, `/api/v1/investigations` и страница дела опрашивались
после каждого шага.

| После шага | Состояние данных | Что видит пользователь | `/health/ready` |
|---|---|---|---|
| — (до миграции) | 1896 из 2231 видимых событий несут дату публикации как дату события | Даты событий, часть из них — на самом деле публикации | 200 |
| 2. Миграция | Подменённые даты сняты, все видимые события без даты | «дата события не установлена» + дата публикации. Неверной даты нет | **200** |
| 3. Re-extract | 9701 новое событие, **ни одно не связано с людьми** | То же: интерфейс читает старые события, у которых дат уже нет | **200** |
| 4. `collect-entities` | Роли и вердикты **стёрты** (2543 → 0, 1308 → 0) | **Список кандидатов и «политические дела» пусты** | **200** |
| 5. `find-figurants` | Роли восстановлены (2536) | Список снова есть, вердиктов ещё нет | **200** |
| 6. `find-political` | Вердикты восстановлены (1308) | Полная картина, даты событий там, где текст их написал | **200** |

Два вывода из таблицы:

- **Неверная дата не показывается никогда.** Промежуточные состояния деградированы, но не
  ложны: страница прямо пишет, что дата события не установлена.
- **Сигнала о деградации нет.** `/health/ready` отвечает `200 ready` на всех шагах, потому
  что схема совпадает уже после шага 2, а compose-healthcheck проверяет только liveness.
  Ничто не остановит трафик и не предупредит — поэтому API надо снимать самому.

Итог полного прогона на копии: видимых через людей событий 2303 (было 2231), из них с датой
события 311, и **ни одно** не равно `published_at` (было 1896 из 1896).

## Проверка

Выполнять после шага 6. Каждый запрос обязан дать ожидаемое значение; расхождение —
стоп-сигнал.

```sql
-- Миграция применена и подменённых дат не осталось
SELECT version_num FROM alembic_version;              -- q1w2e3r4t5y6
SELECT count(*) FROM extracted_events e
  JOIN article_extraction_runs r ON r.id = e.extraction_run_id
  JOIN parsed_articles a ON a.id = r.article_id
 WHERE e.event_date = a.published_at;                  -- 0

-- Повторное извлечение прошло по всем статьям
SELECT count(*) FROM article_extraction_runs
 WHERE extractor_version LIKE '%1.11.0%';             -- 4617
SELECT count(*) FROM article_extraction_runs WHERE status <> 'succeeded';  -- 0

-- Новые события подключены к людям (иначе collect-entities не отработал)
SELECT count(*) FROM extracted_events e
  JOIN article_extraction_runs r ON r.id = e.extraction_run_id
 WHERE r.extractor_version LIKE '%1.11.0%'
   AND EXISTS (SELECT 1 FROM event_entity_mentions em
                JOIN entity_group_mentions gm ON gm.mention_id = em.mention_id
               WHERE em.event_id = e.id);             -- 311+, was 0

-- Роли и вердикты восстановлены (иначе список кандидатов пуст)
SELECT count(*) FROM entity_group_roles;              -- 2536
SELECT count(*) FROM entity_group_politics;           -- 1308

-- Ничего не потеряно
SELECT count(*) FROM person_event_links;              -- 11
SELECT count(*) FROM entity_group_mentions;           -- 12483
```

Пользовательская проверка после возврата API: `/api/v1/investigations` возвращает непустой
список, а в хронологии дела есть «дата события не установлена» там, где текст не называет
дату, и обычные даты — там, где называет.

## Стоп-условия

Остановиться и **не переходить к следующему шагу**, если:

- `docker compose run --rm migrate` завершился ненулевым кодом или с `RuntimeError` —
  миграция сама проверяет, что подменённых дат не осталось, и падает, если они есть;
- `extract-entities` вернул `articles_failed > 0`;
- любой проверочный запрос дал неожиданное значение;
- `collect-entities` прошёл, а `find-figurants` или `find-political` — нет. Тогда продукт
  оставлен со стёртыми ролями и вердиктами: список кандидатов пуст. **Это самое
  неприятное состояние из всех** — вернуться можно только докончив шаги 5 и 6.

Каждый шаг переносим с места: миграция при повторе обновляет 0 строк, `extract-entities`
пропускает уже обработанные статьи, `collect-entities` пересобирает с нуля, шаги 5 и 6
берут ответы из кэша.

## Откат

```bash
# Вернуть даты из backup-таблицы и снять её
docker compose run --rm api alembic downgrade -1
```

`downgrade` восстанавливает ровно те значения, которые сняла миграция, и удаляет
backup-таблицу. Полная отмена всех шести шагов — восстановление дампа из шага 1: после
шага 4 прежние события уже перестали читаться интерфейсом, и `downgrade` их не вернёт.

## Ограничения и типичные ошибки

- **API нельзя оставлять поднятым** — см. таблицу выше. Ничто не мешает пользователю увидеть
  пустой список кандидатов, и ничто об этом не сообщает.
- **Нельзя пропускать шаги 5 и 6.** `collect-entities` стирает роли и вердикты; без них
  продукт работает, но пуст.
- **`extract-entities` не удаляет старые прогоны.** `extracted_events` растёт (на копии
  17622 → 27323). Старые строки после `collect-entities` недостижимы и безвражны, но остаются
  в таблице. Это существующее поведение, а не следствие миграции; отдельное решение об их
  очистке — вне этой процедуры.
- **Шаги 5 и 6 стоят денег** без ограничения бюджета. Проверка на копии шла с
  `ENTITY_MODEL_BUDGET_USD=0` и обошлась в $0.
- **`find-political` тянет список Росфинмониторинга** по сети. Сбой сети не отменяет
  вердикты: стадия отработает и скажет, что список не проверен.
