# Известные риски и заметки

## Текущий статус

- MVP-каркас + вертикальный срез (Etap 0–3). Источники работают на сохранённых fixtures.
- Live-доступ и запись в Airtable отключены до подтверждения маппинга.
- LLM отключена (`CM_LLM_MODE=disabled`); regex-экстракция детерминирована.
- Telegram: `process_registry_source` + `TelegramChannelAdapter` полностью подключены к pipeline (fetch fixture/`--live` → ingest → parse → extract). Ранее `parse_and_extract` безусловно прогонял контент через sudrf-специфичный `parse_press_release`, из-за чего в текст для экстракции подмешивался Telegram UI-мусор (имя канала, "VIEW IN TELEGRAM", плейсхолдеры медиа) — исправлено: для source_type != sudrf используется уже очищенный `doc.text`, sudrf-парсер вызывается только для sudrf-документов. Regression-тесты: `tests/integration/test_telegram_pipeline.py`.
- Etap 4, срез 1: добавлены `ReviewItem` (generic очередь проверки оператора) и `AuditLog` (append-only аудит решений) — миграции `0006_review_items`, `0007_audit_log`. `ReviewItem` создаётся при `parser_status=parser_failed`; `AuditLog` пишется из `update_match_status` (confirm/reject-match) и `resolve_review_item`. CLI: `list-review-items`, `resolve-review-item --dismiss`, `--operator` флаг у `confirm-match`/`reject-match`/`resolve-review-item`. `Person`/`Case`/`CourtEvent` намеренно не введены в этом срезе — см. `technical-debt.md` D-001.
- D-011 (закрыт): `SudrfAdapter`/`TelegramChannelAdapter` теперь возвращают `Iterator[FetchResult | FetchProblem]` вместо молчаливого `continue`/`return None` при блокировке/ошибке/таймауте. `process_source`/`process_registry_source` на `FetchProblem` создают `ReviewItem(item_type="source_blocked")` через `repo.upsert_review_item`, дедуп по `source_id` (не по `document_id`, которого для source-level проблемы нет).

## Ограничения

- **Airtable** — `read_only` режим; PAT не предоставлен. Shared-view читается из fixture.
- **Судебные источники мертвы, и `config/sources.yaml` это маскирует.** Оба sudrf-источника стоят на `backend: fixture`, так что конфигурация выглядит рабочей, хотя живых источников за ней нет: из 379 документов в базе 375 — Telegram, 4 — из сохранённых fixture. Проект называется court-monitor, но суды не мониторит. Разведка 2026-07-30:

| Адрес | Результат |
|---|---|
| `2zovs.sudrf.ru`, `uovs.sudrf.ru` | 404 на **весь домен**, включая `/` и `/index.php` |
| `docs.sudrf.ru` | TCP открыт, HTTP 404 |
| `bsr.sudrf.ru` (Банк судебных решений) | **TCP timeout** (8–45 с, три попытки) |
| `sudrf.ru` | 200, но портал-навигатор: 12 ссылок, контента нет |
| `sudrf.ru/index.php?id=300` (поиск судов) | 200, список рендерится через JS |
| `vsrf.ru` (Верховный Суд) | 200, доступен; `/documents/`, `/lk/practice/acts` отдают каркас с «Выполняется запрос» — тоже JS |

  `bsr.sudrf.ru` = `84.42.111.136`, при этом соседние `84.42.111.138` (`cdep.ru`) и `.139` (`sudrf.ru`) из той же подсети открываются за 0.09 с — то есть недоступен именно этот хост, а не сеть.

  **Гипотеза «это блокировка по географии, VPN поможет» проверена 2026-07-31 и не подтвердилась.** Через российский OpenVPN-туннель (маршрут только для `84.42.111.0/24`, исходящий адрес `10.1.0.17`, трафик подтверждён счётчиками `tun0`):

| Хост | TCP 443 | TCP 80 | ICMP |
|---|---|---|---|
| `84.42.111.136` — БСР | **timeout 12 с** | **timeout 12 с** | 100% loss |
| `84.42.111.139` — sudrf | ok 0.11 с | ok 0.11 с | 108 мс |
| `84.42.111.138` — cdep | ok 0.11 с | ok 0.11 с | — |

  Альтернативной DNS-записи «для России» тоже нет: `192.168.0.1`, `8.8.8.8` и `77.88.8.8` единогласно отдают один и тот же `84.42.111.136`. То есть хост недоступен **для всех**, а не для нас — это не блокировка казахстанского трафика, и VPN направление не открывает. Ветку «поднять VPN и забрать БСР» можно закрыть; остаётся только вопрос, существует ли сервис по другому адресу, а это разведка контента, а не сети. Скрипт замера сохранён: `scripts/probe_sudrf.py` — воспроизводится за минуту, до и после туннеля.

  Практический вывод: восстановление судебных источников — это **не обновление URL**, а новая интеграция. Любой путь упирается в JS-рендеринг, то есть требует `playwright` (ленивый паттерн подключения уже есть в `sources/airtable_registry.py::render_shared_view`).

  **`vsrf.ru` проверен через playwright (2026-07-30) и задачу не решает.** Браузером страницы рендерятся нормально, но нужных данных там нет:

  - `/documents/`, `/documents/own/` — постановления Пленума и обзоры практики, то есть **обезличенные** документы: 0 ФИО, 0 упоминаний даты рождения.
  - `/lk/practice/acts` — форма поиска актов с фильтрами (в том числе «Вид судебного документа: Приговор»). Найденные на ней 399 ФИО вида «Абакумова И.Д.» — это выпадающий список **судей-докладчиков**, а не фигуранты дел; дат рождения на странице нет. Раздел живёт в личном кабинете и требует входа.

  То есть Верховный Суд публикует обобщающие документы, а приговоры с ФИО и датами рождения выносят суды первой инстанции — а это ровно те источники, что недоступны (мёртвые домены + заблокированный БСР).

  **`sudact.ru` разведан 2026-07-31 — доступен, но обезличен.** Это меняет диагноз всей ветки: дело не в доступности, а в законе.

  - Доступность не проблема: `sudact.ru` (0.13 с), `actofact.ru`, `epp.genproc.gov.ru`, `sledcom.ru` отвечают HTTP 200 из Казахстана без VPN. Не отвечает только `pravo.gov.ru`.
  - `robots.txt` разрешает `/regular/doc/` и `sitemap.xml`, но запрещает `/regular/doc_ajax/` — а результаты формы поиска приходят именно через него. Легитимный путь обхода — sitemap: `sitemap_part_0.xml.gz` + `part_1`, только в первой части 19 351 ссылка на `/regular/doc/<id>`.
  - **Тексты обезличены.** Замер по 14 случайным документам: 291 плейсхолдер вида `ФИО1`/`ФИО2` (≈21 на документ), «уроженец/уроженка» — **0**, «года рождения» — 7 (и то рядом с `ФИО1`, без самой даты), даты `ДД.ММ.ГГГГ` местами вырезаны полностью. Встречается и `<данные изъяты>`.
  - Оговорка о границах замера: среди 14 документов не попалось ни одного приговора первой инстанции (только апелляционные определения и постановления, определения, решения). Так что по приговорам это экстраполяция — но обезличивание здесь системное, оно предписано ст. 15 ФЗ-262 для всех публикуемых актов, а не является особенностью апелляции.

  **Пресс-релизы силовых ведомств разведаны 2026-07-31 — тоже не дают ФИО.** Это была последняя неисследованная ветка («источник, публикующий не официальные акты»).

  - **`sledcom.ru` (СК).** `robots.txt` разрешает `/news/`, но требует `Crawl-delay: 20` — соблюдалось. Текст новости лежит прямо в HTML, без обёртки-контейнера: `h1` всегда «Новости», статьи нет ни в `.b-article`, ни в `[itemprop=articleBody]`, реальный текст — в самых длинных `<p>`. Содержание типовое: «в одном из районов Челябинска произошла массовая драка… возбуждено уголовное дело по признакам преступления, предусмотренного ст. 213 УК РФ». **Единственные ФИО в тексте — должностные лица СК** (Бастрыкин А.И., руководитель управления), фигуранты обезличены полностью: «местный житель», «участники конфликта», «несовершеннолетние», «обвиняемый». Дат и мест рождения — 0.
  - **`epp.genproc.gov.ru` (Генпрокуратура).** Контента в HTML нет вообще: 116 КБ разметки, но 0 вхождений «уголовное дело», «приговор», «осуждён», «возбуждено», нет ни `og:title`, ни meta-описания. Новость подгружается динамически — то есть даже чтобы посмотреть, что там, нужен playwright. `robots.txt` при этом запрещает `/api/*`, `*/search/`, `*/feed`, `*/rss`.
  - Методическая оговорка: первый замер по СК был ошибочным — селектор попадал в общий блок ленты, из-за чего три разных материала дали одинаковые счётчики. Вывод выше сделан после того, как контейнер был найден правильно.

  **Вывод: ветка судебных источников закрыта не из-за блокировок, а из-за обезличивания.** Официальная публикация судебных актов в РФ по определению не содержит того, что нужно проекту (ФИО + дата и место рождения) — то же самое ранее показал `vsrf.ru`. Открытие доступа к БСР, если бы оно случилось, дало бы такие же обезличенные тексты. Дальнейшие попытки искать «живое зеркало судов» бесперспективны. Пресс-релизы Генпрокуратуры и СК проверены (см. выше) и тоже обезличены — остаются только СМИ, то есть ровно то, чем уже являются Telegram-каналы.

  **Итог разведки источников (2026-07-30 … 07-31): ФИО вместе с датой и местом рождения в доступных источниках не публикуются никем.** Проверены и закрыты: sudrf.ru (мёртв), БСР (недоступен никому, VPN не помогает), vsrf.ru (обезличено), sudact.ru (обезличено), Генпрокуратура (контента нет в HTML), СК (обезличено). Это означает, что `_score_birth_date` и `_score_birthplace` не оживут за счёт нового источника — при работе с новостными текстами различать однофамильцев придётся по контексту, а не по анкетным данным. Проектное следствие: либо принять это и вкладываться в контекстные признаки (счётчик однофамильцев в реестре и «другие упоминания» уже есть, но на скор не влияют), либо искать доступ к непубличным данным, что за рамками проекта.
- **Live HTTP** — тестирование на удалённых судах недоступно из тестового окружения (404/блокировки). `fedsfm.ru` при этом доступен и из Казахстана (TCP отвечает за 0.1 с, HTTP 200, ни капчи, ни Cloudflare) — единственной преградой был TLS, см. пункт про SSL ниже; VPN не требуется.
- **Экстракция ФИО** — эвристика, не полный морфологический анализ. Возможны пропуски и ложные срабатывания. Обнаружено на реальных live-данных (`run-all --live` по всем Telegram-каналам): юридический ALL-CAPS дисклеймер про «иностранного агента» и аббревиатуры (ООО, СБУ, «РБК-Украина», «ЛГБТ-активистки») массово ловились как ФИО — исправлено в `extraction/names.py::_is_boilerplate_caps`: отклоняется любой токен (или дефисная часть токена) с более чем одной ALL-CAPS буквой, поскольку настоящие ФИО всегда Title Case, а инициалы («И.») — однобуквенные и под фильтр не попадают. **Найден и исправлен баг класса символов**: `_TOK` читался как `[а-яёA-ЯЁ\-']`, где `A` — *латинская* (U+0041), а не кириллическая `А` (U+0410). Диапазон `A-Я` покрывал **1006 кодовых точек**: всю латиницу, знаки препинания и символы, включая `«` (U+00AB) и `»` (U+00BB). Отсюда «Андрей Воробьев»», «Аэрофлота» Михаила Полубояринова», «Ведомостей» Максим Трудолюбов». После исправления кавычки пришлось добавить в lookahead как терминаторы — иначе имя перед закрывающей кавычкой стало бы теряться. Замер на 379 документах: имён с мусором **48 → 0**, при этом появился 31 новое имя, потому что кавычка больше не съедает человека. Добавлены `_COLLECTIVE_HEADS` (Жители/Власти/Администрация — группа или институция, человека за ними нет, отбрасывается целиком) и `_LEADING_NOISE` (Сам/Позднее/Ранее — ведущее служебное слово отсекается, а не отбрасывает запись: «Сам Джаред Лето» содержит реального человека).

  **Остаточная (не исправленная) проблема того же класса** — склейка топонима/институциональной фразы в родительном падеже с настоящим именем («Владивостока Татьяны Намазбаевой», «Армении Николом Пашиняном», «Житель Ингушетии Ибрагим») — требует геозетеера/морфоанализа (Etap 6), не эвристики стоп-слов.
- **Скоринг по дате и месту рождения не работает не из-за скоринга.** `_score_birth_date` и `_score_birthplace` написаны и протестированы, и в реестре данные есть практически везде (даты у 21 511 из 21 511, места у 21 428). Мёртвая половина — вторая: в текстах документов их нет. Замер по 379 документам: признак даты рождения нашёлся в **5**, места рождения — в **0**. Telegram-новости не пишут «1980 года рождения, уроженец Москвы» — это формулировка судебных актов, а судебные источники не работают (см. выше). Поэтому все кандидаты имеют ровно `0.50` (`W_SURNAME_NAME_MATCH`) — сам по себе score в этой ситуации не различает никого. **Частично компенсировано ранжированием очереди по контексту** (`MatchCandidate.namesakes` / `other_mentions`, миграция `0012`): наверх попадают редкие фамилии и имена, подтверждённые несколькими документами. На реальной базе это ставит Екатерину Шульман и Гарри Каспарова (по 1 однофамильцу) выше Дмитрия Медведева (16). Score при этом не трогается — он остаётся утверждением о сходстве имени/даты/места, а контекст живёт отдельными измеренными числами.

  **Второй компенсатор — суждение LLM** (`court_monitor/llm/`, миграция `0013`, CLI `judge-matches`). Модель читает документ и говорит, согласуется ли описанное лицо с записью реестра, приводя цитату. Это подсказка оператору: в `score` не входит, `status` не меняет. Прогон по всем 14 кандидатам рабочей базы (DeepSeek `v4-pro`): **13 `insufficient`, 1 `contradicts`**, ошибок 0, ~10 с и ~0.1 ¢ на кандидата. Единственное сработавшее суждение содержательно: по упоминанию должности («зампред Совбеза») модель поняла, что это Дмитрий *Анатольевич* Медведев, а в реестре — Дмитрий *Максимович* 2003 г.р.

  **Промпт откалиброван консервативно, и это рычаг.** Текущая формулировка прямо разрешает ответ «мало данных» и просит не угадывать — отсюда 13 из 14. В более раннем прогоне с менее осторожным промптом та же модель на «губернатора Воробьёва» отвечала `contradicts`. Для реестра террористов консервативность выбрана намеренно (ложное «совпадает» дороже ложного «не знаю»), но если полезность окажется низкой — калибруется правкой `_PROMPT` в `llm/disambiguation.py`, без изменений в коде.

  **Суждения недетерминированы**, в отличие от скоринга: один и тот же кандидат может получить разные вердикты между прогонами. Поэтому они и не участвуют в `score` — воспроизводимость решения о человеке важнее. Доработка экстракторов сама по себе ничего не даст — нужен источник. (Экстрактор места рождения с тех пор написан, см. ниже; вывод это не меняет — писать он может только то, чего в текстах нет.)
- **Нормализация дат рождения** — year-only precision не fabrication month/day, но сравнение less precise.
- **CAPTCHA/блокировки** — не обходятся; при `FetchHealth.blocked`/`http_error`/`timeout` создаётся `ReviewItem(item_type="source_blocked")` (D-011, закрыт). `304 Not Modified` и отсутствие локальной fixture (dev/test) ReviewItem не создают — это не сбой источника.
- **SSL** — не отключается нигде, `verify=False` в рабочем коде отсутствует. Для `fedsfm.ru` вместо этого пиннится цепочка: сертификат выдан УЦ Минцифры, которого нет ни в системном хранилище, ни в `certifi`, поэтому `config/ca/fedsfm_ru_chain.pem` передаётся через `HttpClient(verify=…)` только этому клиенту — верификация остаётся включённой, и этот УЦ не может подтверждать остальные хосты проекта. **Остаточный риск**: оба сертификата впервые скачаны по соединению, которое ещё нельзя было проверить, то есть пиннинг даёт непрерывность, но не аутентичность. Подробности и ротация — в `config/ca/README.md`.
- **Дубли при смешивании CSV- и HTML-импортов РФМ** — дедуп идёт по `(source, normalized_name, birth_date)`, но в `rosfinmonitoring-2.csv` дат рождения нет вообще (только «возраст при включении»), а живая HTML-страница даёт дату каждому человеку. Один и тот же человек получает разные dedup-ключи и попадает в базу дважды. Замер на реальной БД: 21 277 из 22 156 имён пересекаются, импорт отрапортовал `duplicates=0`, база выросла 22 156 → 43 667. Логика дедупа **намеренно не менялась** — именно она не даёт схлопнуться настоящим однофамильцам. `fetch-source fedsfm --live` громко предупреждает перед записью, если в базе есть записи rfm без дат. Правильное решение (замена перечня вместо дозаписи либо обогащение существующих записей датами) — отдельная задача.
- **Живой перечень РФМ отдаёт не всё** — из 23 220 записей страницы распознаётся 21 511 физлиц. Организации и записи вида «ОБЪЕДИНЕНИЕ, ЧЛЕНАМИ КОТОРОГО ЯВЛЯЮТСЯ: …» (несколько людей в одной строке) не ложатся в `PersonRecord` и попадают в `ParseResult.unrecognized`, а не отбрасываются молча — смена вёрстки проявится скачком этого счётчика.
- **spaCy NER** — по умолчанию выключен (`CM_NER_MODE=disabled`). Даёт выше precision, чем regex (66 против 52 попаданий в реестр при меньшем числе фактов), но медленнее в ~255 раз (10.6 мс/документ) и требует модель ~500 МБ. ~~При отсутствующей модели `_get_nlp` не кэширует исключение, поэтому попытка загрузки и лог ошибки повторяются на каждый документ.~~ Исправлено: `_load_attempt` кэширует и успех, и неудачу (`lru_cache` сам по себе исключения не запоминает), поэтому `spacy.load` вызывается один раз и ошибка пишется в лог один раз. | Вход | `_normalize_date` | `BirthDateEvidence` | `_extract_year` |
|---|---|---|---|

| `15.06.1983` | `1983-06-15` | full | **`None`** |
| `5.6.1983` | `1983-06-05` | **none** | `None` |
| `19830615` | `1983-06-15` | **year** (первые 4 цифры как год) | `1983` |

Это не уборка дублирования, а продуктовое решение (как и вопрос про недостижимую ветку `birth_date_conflict`, которую это дублирование и держит живой). Делать вместе с решением по ветке, не раньше.
