# ADR 0019: Telegram-бот как внешний адаптер

Статус: принято (2026-09-19)

## Контекст

Оператору нужен способ запускать докачку и смотреть людей из новостей, не заходя на
хост и не открывая локальную веб-морду (ADR 0014: она привязана к localhost). Первая
версия бота должна уметь ровно две вещи: запустить инкрементальное обновление и
показать людей из новостей за период.

Бот управляет живой базой, поэтому цена ошибки высокая: второй параллельный запуск
pipeline, утечка токена в git или доступ постороннего к `/update` недопустимы.

## Решение

### Бот — адаптер, а не вторая реализация pipeline

```text
Telegram command → handler → application service → PostgreSQL / monitoring pipeline → ответ
```

Handlers не содержат SQL, extraction, entity resolution, классификации и сверки с
перечнем РФМ. `/update` вызывает `OperationRegistry.start("monitor", …)` (ADR 0016),
то есть ту же операцию «Докачать новые публикации», что и операторская консоль:
её запись в `operator_operation_runs`, её подпроцесс `main.py monitor --catch-up`,
её heartbeat и её partial unique index `uq_operator_operation_runs_active_operation`,
который и запрещает второй активный run. Handler не ждёт окончания: `start()`
возвращается сразу после записи run.

`/status` читает тот же run и агрегирует `monitoring_runs`, которые оставил его
процесс (ADR 0013) — те же поля, что показывает веб-морда, без выдуманных метрик.

`/people` — единственный новый запрос к базе: один SQL без N+1 (см.
[Telegram-Bot](../wiki/Telegram-Bot.md)).

### aiogram 3

Рассмотрены aiogram 3 и python-telegram-bot. Выбран **aiogram 3.31**:

- поддерживает Python 3.13 (проект требует `>=3.13`);
- long polling и graceful shutdown из коробки (`start_polling(handle_signals=True)`),
  собственный HTTP-цикл писать не нужно;
- handler — обычная async-функция; в тестах он вызывается напрямую, без сети и без
  фейкового Telegram API, поэтому вся логика команд покрыта юнит-тестами;
- зависимости: `aiohttp`, `pydantic`, `magic-filter`, `aiofiles` — pydantic уже в
  проекте, остальное небольшое.

python-telegram-bot тянет httpx (уже есть), но его handlers жёстче завязаны на
`Application`/`ContextTypes`, а тесты требуют больше фейков.

Ручная реализация Bot API поверх `httpx` отвергнута: это собственный цикл polling,
ретраи и разбор update'ов — то, что библиотека делает надёжнее.

### Закрыто по умолчанию

`TELEGRAM_ALLOWED_USER_IDS` — числовые Telegram user id. Пустой allowlist не
переводит бота в read-only, а не даёт ему стартовать: бот без списка — это бот,
которому некого обслуживать, а `/update` пишет в живую базу. Allowlist закрывает
**все** команды, включая `/people`: публичный режим потребовал бы отдельного
решения и отдельной конфигурации.

Решение об авторизации логируется (`event=telegram_authorization`), текст сообщений —
никогда. Токен не хранится в репозитории и не попадает в лог: `redacted()`
заменяет его на `***`.

### Long polling, отдельный процесс

Webhook, публичный HTTPS, открытый порт и reverse proxy не нужны: процесс сам
ходит в Telegram. Бот запускается как `python -m telegram_bot` (профиль compose
`telegram`), а не внутри CLI court-monitor, чтобы бесконечный polling-цикл не
смешивался с одноразовыми командами.

## Последствия

- Бот наследует гарантии operation runs: идемпотентность, дедупликацию, checkpoint
  и защиту от параллельного запуска — без собственного кода.
- `/status` показывает только те метрики, которые pipeline действительно сохраняет.
- Новая зависимость в основном образе (aiogram и aiohttp) — образ используется и
  ботом, и API.
- Добавлены два индекса под запрос `/people` (миграция `v6w7x8y9z0a1`):
  `ix_parsed_articles_published_at` и `ix_extracted_events_extraction_run_id`.
- Первая версия не умеет ничего писать в домен: ни review, ни правку Person, ни
  публикацию в канал.
- `/status` связывает операцию с её monitoring-runs по интервалу и триггеру `manual`,
  потому что `monitoring_runs` не хранит `operation_run_id`. Параллельная ручная
  докачка из CLI или Dagster попадёт в те же счётчики. Так же считает операторская
  веб-морда; развязать это можно только колонкой `operation_run_id` в `monitoring_runs`,
  что выходит за рамки первой версии бота.
- Новостные источники определяются реестром кода (`news_source_base_urls()`), а не
  колонкой в таблице `sources`: смена `base_url` источника отрежет его прежние статьи
  от `/people`. Хранение `kind` в БД — следующий шаг, когда источники начнут меняться.

## Альтернативы

- **Свой запуск `MonitoringService` в процессе бота.** Отвергнуто: дублировал бы
  operation runs, а долгая работа внутри polling-процесса мешала бы отвечать на
  команды и терялась бы при рестарте контейнера.
- **Фильтровать реестр «Мемориала» по имени источника.** Отвергнуто: строковая
  проверка ломается при переименовании. Вместо этого у `SourceDefinition` появился
  `kind: SourceKind` (`news` / `registry`), а запрос фильтрует по базовым URL
  новостных источников реестра.
